## 强制规则

- 行为测试：当新增或修改可观察行为时，必须优先新增或更新能证明该行为的自动化测试。
- BUG 复现：当修复 BUG 时，必须先建立可复现信号；无法自动化时必须记录手动复现步骤、原因和预期结果。
- 测试位置：新增测试必须放入仓库已确认的测试目录，并遵循所在模块命名和夹具风格。
- 外部依赖：测试中必须隔离不可控外部依赖；Mock、Stub、Fake 或测试容器的使用必须符合仓库现有模式。
- 验证记录：交付时必须说明运行的测试命令、结果、未验证项和手动验证步骤。

## 推荐规则

- 优先用聚焦测试证明变更，再按风险补充集成、契约、持久化或回归测试。
- 优先复用已有测试夹具、构造器、测试数据和断言工具。
- 对时间、随机数、并发、缓存和外部接口应使用可控输入，降低 flaky 风险。

## 禁止事项

- 禁止用手动验证替代可行的自动化测试。
- 禁止提交依赖真实生产服务、真实账号、真实敏感数据或不可重复环境的测试。
- 禁止为通过测试而削弱断言、删除关键测试或扩大跳过范围。

## 例外机制

- 若无法自动化测试，必须记录原因、手动步骤、预期结果、风险和后续补测建议。
- 若测试会修改受版本控制文件或需要外部服务，必须先说明影响并获得确认。

## 验收检查

- [ ] 每个实现任务都有自动化或手动验证方式。
- [ ] BUG 修复包含复现、根因、回归和手动验证。
- [ ] 测试不依赖敏感数据和不可控外部状态。
- [ ] 无法自动化的验证已说明原因和补救路径。
