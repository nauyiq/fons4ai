## 强制规则

- 模块边界：当新增代码文件时，必须放入与职责匹配的模块、包和目录；不得为了调用方便跨层放置。
- 依赖方向：当新增模块依赖或包依赖时，必须保持现有依赖方向；底层模块不得依赖应用层、接口层或启动层。
- 配置位置：当新增配置、常量、策略、适配器、工具类或共享能力时，必须放在仓库已有约定位置；没有约定时先标记为 `待确认`。
- 资源位置：当新增资源、脚本、迁移、模板或测试夹具时，必须进入对应 source/resource/test/migration 目录，不得散落在业务代码目录。
- 规则与知识位置：项目规则放入 `.specify/rules/`；SDD 产物放入 `specs/`；长期知识默认放入 `.specify/memory/`；DDL 知识默认放入 `.specify/sql/`。
- 领域边界：采用 DDD-lite 时，必须按当前仓库已有结构映射 domain/application/infrastructure/adapter 职责；不得为了单个功能强行新增完整 DDD 包层级。

## 领域边界规则

- domain 或等价领域层应承载业务对象、领域行为、不变量和状态流转，不应依赖 controller、HTTP/RPC、MQ、mapper、repository 实现或数据库细节。
- application 或 service 层优先承载用例编排、事务边界、权限检查、外部协作和持久化协调，不应长期堆积可下沉的核心业务规则。
- infrastructure、adapter、persistence 代码应作为外部系统、存储和技术细节的适配边界；若项目没有这些命名，必须映射到现有等价目录而不是臆造新层。

## 推荐规则

- 优先让目录结构反映稳定职责，而不是临时实现步骤。
- 优先复用现有模块与包；仅当已有边界无法承载新职责时才新增模块。
- 优先用 DDD-lite 方式保持领域边界清晰，但简单 CRUD、纯查询和薄包装逻辑可以沿用现有轻量结构。
- 新增共享工具前应确认是否已有等价工具，避免多个模块复制相同能力。

## 禁止事项

- 禁止臆造不存在的模块、CI、发布目录或架构层级。
- 禁止让 infrastructure、adapter、persistence 代码反向污染 domain 或 application 边界。
- 禁止为了单个功能创建长期难维护的横向公共包。

## 例外机制

- 若必须新增模块或调整依赖方向，必须先有技术方案说明动机、替代方案、影响范围和验证方式。
- 若项目处于 New Project Mode，可采用默认结构建议，但必须标为 `默认建议`，不得描述为既有事实。
