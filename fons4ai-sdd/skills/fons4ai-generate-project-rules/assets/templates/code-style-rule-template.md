## 强制规则

- 命名规则：当新增包、类、方法、字段、常量、DTO/VO/BO、实体、枚举或测试类时，必须遵循当前仓库已确认命名风格；若无稳定风格，使用本文件的默认建议并标记来源。
- 依赖注入规则：当新增服务、组件、适配器或配置类时，必须使用仓库现有依赖注入方式；禁止混用未被仓库采用的注入风格。
- 工具包规则：当处理字符串、集合、日期时间、IO、Bean 转换、判空、断言、编码、加解密或脱敏等通用逻辑时，必须按 JDK 标准库 -> 项目已有工具类/基础组件 -> 已引入三方工具包 -> 新增依赖的顺序选择工具。
- 依赖新增规则：新增 Hutool、Apache Commons、Guava 或其他三方工具包前，必须在设计方案或用户确认中说明原因、替代方案、影响范围和验证方式。
- 领域表达规则：采用 DDD-lite 时，核心业务规则、状态流转、校验和不变量必须优先由领域对象、领域方法或明确的领域服务表达；简单 CRUD、纯查询和薄包装逻辑可保持轻量实现。
- 异常规则：当新增业务异常、参数校验或外部调用失败处理时，必须保持现有错误码、异常层级和返回格式；无法确认时必须标记为 `待确认`。
- 日志规则：当新增关键业务路径、异常路径或外部交互日志时，必须记录可排查信息，禁止输出密钥、令牌、身份证号、手机号、生产数据或敏感报文。
- 注释规则：当新增关键逻辑、复杂分支、领域字段含义、非显然兼容处理时，必须添加简洁注释说明意图和边界。

## 工具包与依赖使用规则

- Java 项目中，如果已引入 Hutool、Apache Commons、Guava 等成熟工具包，处理其覆盖的通用能力时应优先复用，避免重复手写脆弱逻辑。
- 未确认项目已引入某个三方工具包时，不得擅自新增依赖；只能使用 JDK、项目已有工具类，或在设计中提出依赖新增建议。
- 若选择手写工具逻辑，必须满足：逻辑足够简单、没有已确认可用工具、测试覆盖边界条件，并在实现说明中记录原因。

## 可读性规则

- 方法名、变量名和领域对象名必须表达业务意图，避免使用 `data`、`temp`、`obj`、`handle` 等无法说明含义的名称。
- 复杂条件必须拆分为具名变量或私有方法；多层嵌套应通过提前返回、策略拆分或领域方法降低阅读成本。
- 关键转换流程必须清晰展示输入、校验、转换、持久化或输出步骤，不得把多类职责压缩进单个长方法。

## 领域表达规则

- 领域行为应使用业务语义命名，例如 `approve`、`cancel`、`changeOwner`，避免只暴露 `setXxx` 后由外部服务散落修改状态。
- 充血模型优先用于承载稳定业务规则、状态流转、金额/数量/权限等不变量；贫血模型仅在简单数据承载、查询投影、兼容旧结构或规则尚不稳定时作为例外。
- 应用层方法应表达用例编排，不应隐藏大段可下沉到领域对象的业务判断；如果业务规则留在应用层，必须记录原因。

## 复杂度控制规则

- 新增方法应保持单一职责；当一个方法同时处理校验、查询、转换、持久化、外部调用和响应组装时，必须拆分。
- 对循环、分支、异常处理和外部调用交织的逻辑，必须优先拆分为可测试的小步骤。
- 不得为了少写代码牺牲可读性；链式调用过长、Lambda 嵌套过深或 Optional 滥用都需要重构。

## 重复代码控制规则

- 新增重复逻辑前必须搜索已有工具类、基础组件、三方工具包和相邻模块实现。
- 相同业务规则或通用转换出现第二处时，应优先抽取到已有合适位置；无法抽取时必须说明边界差异。
- 禁止复制粘贴已有实现后只改少量字段，除非已记录短期兼容原因和后续收敛计划。

## 推荐规则

- 优先复用仓库已有工具类、基础类型、错误处理、日志格式和校验方式。
- Java 项目已引入 Hutool、Apache Commons 或 Guava 时，优先使用其成熟方法处理常见工具逻辑。
- 优先让方法保持单一职责；复杂流程应拆成能用测试覆盖的私有方法或领域方法。
- 优先使用 DDD-lite 的领域方法表达核心业务行为，让业务规则贴近领域对象，而不是散落在 controller 或 application service 中。
- 优先使用已有类型表达业务含义，避免引入只服务当前一处调用的过度抽象。

## 禁止事项

- 禁止引入与现有代码风格冲突的新框架、新注解体系或新工具库，除非设计文档明确批准。
- 禁止在已有可用工具包或项目工具类时重复手写字符串、集合、日期时间、IO、Bean 转换、判空和断言逻辑。
- 禁止在领域对象外部通过多处 `setXxx` 或字段拼装绕过领域不变量；确需贫血模型时必须说明它只是数据承载、查询投影或兼容旧结构。
- 禁止把格式化、重命名、无关重构混入功能变更。
- 禁止将临时调试日志、未验证猜测或敏感数据写入代码、测试或规则文档。

## 例外机制

- 如果必须偏离本规则，必须在实现说明或 SDD 产物中记录触发条件、偏离原因、影响范围和验证方式。
- 如果现有代码存在多种风格，优先遵循当前修改模块内的主流风格，并把全局统一问题列入 `待确认约定`。

## 验收检查

- [ ] 新增代码命名、注入、异常、日志和注释风格与所在模块一致。
- [ ] 常见工具逻辑已优先复用 JDK、项目工具类或已引入三方工具包。
- [ ] 新增依赖已在设计方案或用户确认中记录原因、替代方案和影响范围。
- [ ] 复杂逻辑已拆分到可读、可测、单一职责的方法或对象。
- [ ] 核心领域行为已通过 DDD-lite 方式放在合适的领域对象、领域方法或领域服务中，贫血模型例外已有理由。
- [ ] 没有新增可通过工具包或已有工具类替代的重复代码。
- [ ] 没有引入未被批准的新框架、库或风格体系。
- [ ] 敏感数据没有出现在日志、异常、测试数据或文档中。
- [ ] 所有默认建议和待确认项都被明确标注，未伪装成仓库事实。
