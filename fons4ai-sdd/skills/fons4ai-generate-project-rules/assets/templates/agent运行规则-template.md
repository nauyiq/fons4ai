## 核心原则

- 修改代码前必须先理解需求，确认目标、范围、输入输出和验收方式。
- 优先复用已有代码、工具函数、组件、领域对象、异常处理和测试模式，不重复造轮子。
- 优先遵循项目规范和当前模块风格，而不是模型默认习惯。
- 不允许修改与当前需求无关的代码、配置、文档或格式。
- 不允许引入新的技术框架、运行时、构建工具或核心依赖，除非用户明确要求或方案已确认。
- 不允许删除核心业务逻辑、关键校验、权限控制、审计逻辑或异常处理。
- 不允许修改数据库结构、迁移脚本或 DDL 规则，除非需求明确涉及数据模型变更。
- 不确定的事实必须标记为 `待确认`，不得包装成已验证结论。

## MCP使用规则

- MCP 只作为受控工具能力使用，不能替代需求澄清、代码阅读、事实判断和用户确认。
- 使用 MCP 前必须确认项目已配置对应服务；未配置或无法确认时，不得假设 MCP 可用。
- 涉及数据库、外部系统、知识库、浏览器、文档或其他 MCP 时，必须先确认使用目的、数据范围和风险边界。
- 默认优先使用只读 MCP 能力；涉及写入、删除、更新、发送请求、执行变更或影响外部系统的操作，必须先获得用户明确确认。
- 存在多个候选 MCP 服务、数据库、环境或账号时，必须先询问用户选择，不得自行合并多个来源的结果。
- MCP 返回内容只能作为事实来源之一；重要结论必须结合仓库代码、配置、文档或用户确认交叉验证。
- 不得把 MCP 工具名称、连接信息、查询语句、令牌、账号、内部地址或敏感返回内容写入长期文档、日志或提交内容，除非项目明确要求记录且已脱敏。

## 输出要求

每次修改代码后必须说明：

- 修改原因；
- 修改内容；
- 涉及文件；
- 潜在风险；
- 测试或验证建议；
- 是否存在待确认事项。

## 禁止事项

禁止：

- 猜测业务逻辑；
- 编造接口；
- 编造数据库字段；
- 编造第三方 API；
- 编造配置、环境变量、部署流程或 CI 流程；
- 输出未经验证的结论；
- 用大范围重构掩盖小需求；
- 删除或覆盖用户已有改动；
- 在未确认的情况下提交敏感信息、密钥、令牌或真实生产数据。

## 信息不足时的处理

- 如果信息不足以安全执行，应主动说明缺失信息。
- 如果可以先做低风险调研，应先调研并列出发现。
- 如果需要用户决策，应给出推荐方案、理由和可选项。
- 如果只能基于假设继续，必须明确标记假设，并等待用户确认后再执行高风险改动。
