## 强制规则

- 需求门禁：当新增功能、行为变更、公共接口变更、数据模型变更或权限安全变更时，必须先完成需求澄清和可测试验收标准。
- 设计门禁：当变更跨模块、影响公共行为、涉及数据模型、事务、缓存、MQ、权限或兼容风险时，必须先完成技术方案。
- 任务门禁：进入实现前必须有明确任务范围、影响文件、验证方式和完成标准；不得实现未计划范围。
- 上下文门禁：进入需求、设计、任务或实现前，必须先用关键词、模块名、业务对象、表名、接口名、错误信息或 AC/REQ 编号定位上下文；不得默认全量读取所有知识库文件。
- 复用规则：实现时必须优先复用已有工具、组件、领域对象、异常模型和测试模式。
- DDD-lite 规则：核心业务规则、状态流转、校验和不变量必须优先放入领域对象、领域方法或领域服务；应用层优先负责编排。
- 知识同步：当变更形成长期业务、技术、数据或治理事实时，必须标记知识同步需求，并通过指定流程汇总到真理源。

## DDD-lite 实现规则

- 业务行为归属：能由业务对象自己判断和修改的规则，应优先进入领域对象或领域方法；跨对象协作且不属于单个对象时，才考虑领域服务。
- 充血模型：稳定的状态流转、金额/数量计算、权限约束、生命周期约束和业务不变量，优先封装在充血模型中。
- 贫血模型例外：简单 CRUD、纯查询、DTO/VO、数据库映射对象、查询投影、兼容旧结构或规则尚不稳定时，可以保持贫血模型，但必须避免把核心规则散落到多处。
- 应用层职责：应用服务负责用例编排、事务、权限、外部协作和持久化协调；不应长期承载可下沉的核心业务规则。

## 推荐规则

- 小型安全修改可以轻量化处理，但仍需先调研上下文并说明验证方式。
- 上下文读取优先采用“文件清单 -> 关键词搜索 -> 相关章节/文件 -> 必要时扩大范围”的顺序。
- 普通功能优先采用 S1；高风险功能采用 S2，并补充 checklist、回滚、兼容、安全和迁移说明。
- 功能实现应按 Red-Green-Refactor 推进：先暴露行为，再实现，再做必要整理。
- 简单功能不强行 DDD 化；复杂业务行为应在设计阶段明确领域对象、值对象或领域服务候选。

## 禁止事项

- 禁止在需求不清、验收标准缺失或影响范围未知时直接编码。
- 禁止因为存在 `.specify/memory/`、`.specify/sql/`、`.specify/rules/` 或 `docs/` 就默认全量加载所有文件。
- 禁止把本应属于领域对象的业务规则长期堆在 controller、application service、mapper 或 adapter 中。
- 禁止推倒重写已完成 SDD 产物；已完成功能的增量调整必须走变更流程。
- 禁止把临时调试、废弃方案或未验证假设写入长期知识库。

## 例外机制

- 若用户明确要求跳过完整 SDD，必须说明风险，并至少保留调研结论、改动范围和验证方式。
- 若实施中发现计划错误或范围扩大，必须暂停并回到需求、设计、任务或变更流程补齐约束。
