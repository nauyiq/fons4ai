## 现象

用户的核心目标是让框架层和现有 Agent 暴露统一审批能力，审批点是否启用以及如何编排由下游决定。执行产物最终同时引入或规划了公共审批协议、Run 与 Approval 双状态机、checkpoint、跨实例恢复、CAS、恢复 fencing、事件游标、审计、加密、保留策略、Redisson 逻辑结构、五类 Agent 适配及真实 Graph 恢复验证。

任务规划共 10 项，按“未指定任务 ID时执行全部未完成任务”的规则一次性启动。任务模板展示任务数量、依赖和风险，但没有提供以下负责人可快速判断的信息：

- 本轮是最小框架能力、生产加固，还是完整分布式恢复平台；
- 将新增多少公共抽象、状态机、持久化结构和供应商适配；
- 哪些能力是当前接入必需，哪些可以等待第一个下游接入后再实现；
- 预计执行轮次、验证成本和触发重新确认的复杂度阈值；
- 一个不包含 CAS、fencing、outbox、跨实例恢复的最小替代方案。

独立 Spec Review 和 Code Review 集中在 T009 之后执行，发现恢复终态关联、当前审批索引、事件原子性、真实 Graph 恢复和 Redisson 数据结构等问题。实现过程随后继续增加恢复 completion 契约、RunApprovalIndex、补偿和测试，而没有先暂停并让用户在“继续生产级加固、缩减 V1、延期非关键项”之间重新选择。

最终表现为：

1. 单次执行持续约两个半小时，期间缺少面向用户的复杂度和剩余工作量止损点。
2. 负责人明确反馈整体设计难以理解，说明 SDD 的“通俗解释”不足以支撑架构级决策。
3. 评审发现的是架构闭环问题，而不只是局部代码缺陷；继续直接修复会进一步扩大公共契约和持久化语义。
4. 最近一轮架构修正后的完整回归尚未完成，不能把此前 105 项测试结果继续作为当前最终实现的完整 L3 证据。

## 期望行为

同类 S2 框架功能应增加“复杂度预算与阶段化交付 Gate”：

1. 需求或设计阶段必须同时给出“最小可用方案”和“生产加固方案”，用负责人可理解的语言列出两者的新增抽象、运行状态、存储依赖、供应商耦合、验证成本和暂缓项。
2. 任务规划应新增复杂度摘要，至少包含改动模块数、公共 API/状态机/持久化结构数量、跨实例或分布式一致性要求、预计验证矩阵和建议分批任务。
3. 当 S2 任务同时涉及多个模块、公共协议、持久化、跨实例恢复或供应商内核时，用户回复“执行全部任务”前应再次展示一页式影响摘要，并推荐先执行最小闭环任务集。
4. 实现过程中出现以下任一条件时必须暂停，而不是继续补架构：
   - 独立 Review 需要新增公共契约、状态机或数据结构；
   - 同一阶段出现第二轮架构级 Critical；
   - 实际改动面超过任务规划中的复杂度预算；
   - 执行时长或验证轮次超过预设检查点。
5. 暂停后应让用户明确选择：继续生产级加固、缩减为 V1、延期 Important、或进入 SDD Change；不得把 Review 的所有建议默认转化为当前实现任务。
6. 对框架项目，应把“真实下游首次接入验证”和“框架仓库当前必须实现”分开。没有下游宿主时，不应仅为获得完整 Evidence 而提前实现所有生产拓扑能力。
7. Spec Review 应在核心公共契约和恢复边界完成后增加一次中期架构 Review，再进入五类 Agent 的批量适配，避免在末尾才发现基础抽象不闭环。

## 初步归因

- 归因结论：可抽象为上游规则和模板缺口，跨项目重复性待观察。
- 归因说明：
  - `fons4ai-sdd-implement` 已规定“不扩大 AC”“发现冲突及时停止”，但没有定义复杂度预算、长时间执行检查点，以及 Review 建议何时属于设计变更而非普通实现修复。
  - `tasks-template.md` 记录任务数量、风险和依赖，却没有负责人可读的实施规模、最小替代方案、预计验证成本或分阶段交付建议。
  - 当前 S2 流程把独立 Review 放在末尾，导致基础架构问题在大量适配完成后才暴露，修复成本和设计复杂度被放大。
  - 本次执行也存在 Agent 未充分遵守“发现范围扩大及时停止”的本地执行偏差，不能把全部责任归因于上游技能。
- 不确定项：尚未确认其他项目是否也出现“全量 S2 实现长时间运行且负责人无法判断复杂度”的重复案例；具体时间阈值应由上游结合运行环境确定。
- 证据约束：当前只有单项目证据，结论范围仅限本次试点，不将本次项目设计问题直接等同于 Harness 缺陷。

## 是否建议回流上游

- 建议回流：待观察。
- 判断依据：用户已明确确认执行时间和设计可理解性不符合预期，现有 skill/template 文本也确实缺少复杂度预算与架构级 Review 止损字段；但尚无第二个项目的重复证据。
- 若不立即回流，应留在业务项目的处理位置：暂停当前人工 Gate，将审批能力重新拆分为最小框架契约与后续生产加固两个阶段，再决定保留或回退现有实现。

## 建议修改位置

- skill：
  - `fons4ai-sdd-design/SKILL.md`：要求 S2 框架设计提供“最小方案/生产加固方案/暂缓项”对比和负责人可读的一页式摘要。
  - `fons4ai-sdd-tasks/SKILL.md`：对高复杂度任务生成分阶段建议，默认不把全部生产加固项放入首批实现。
  - `fons4ai-sdd-implement/SKILL.md`：增加全量 S2 启动前复杂度复核、定期进度检查点，以及 Review 触发公共契约或数据结构变更时停止并转 SDD Change 的规则。
- template：
  - `fons4ai-sdd-tasks/assets/templates/tasks-template.md`：在“任务概览”增加复杂度预算、负责人可读影响摘要、最小首批任务、延期任务和预计验证成本字段。
  - 技术设计模板：增加“最小可用架构与生产加固架构对比”章节。
- script：无直接脚本缺陷证据。
- docs：补充 S2 框架项目的阶段化交付示例，说明下游接入验证不得反向扩大当前框架实现范围。
- validator：增加提示型校验；当任务同时命中公共 API、多个模块、状态机、持久化、跨实例/分布式一致性和供应商适配时，要求存在复杂度预算及分阶段 Gate。该校验宜告警并要求确认，不宜机械阻止所有大型任务。
