## 3. 范围调整结论

### 3.1 真实 Redis 多实例联调

结论：**本轮不启动真实 Redis 多实例联调是合理的，不应作为 T008 或当前框架制品验收门禁。**

理由：

- 当前交付是库/Starter，不是独立可部署服务；没有下游宿主应用、节点数量、Redis 模式、网络、发布顺序与回滚拓扑，强行启动“多实例联调”无法形成具有代表性的验收环境。
- 本轮需求关注任务身份、租约格式、精确停止、迟到终态和 CAS 删除等框架契约，这些可通过确定性替身测试验证。
- 真实多节点停止、TTL、混合版本升级和回滚行为依赖实际宿主部署，应作为下游接入检查项，而不是把未来接入条件反向设为当前框架任务的阻塞条件。

边界要求：该调整不等于永久免验。下游接入清单仍应保留真实 Redis 多节点、发布顺序、混合版本禁止策略、停止消息、TTL 与回滚验证。

### 3.2 宿主侧配置

Alibaba/Spring AI 的生产日志级别、宿主 Redis 配置和宿主扩展实例的线程安全，只能由下游应用在接入阶段确认。当前框架门禁应验证的是：框架自身不输出敏感正文、公共扩展契约明确线程安全责任、默认配置与文档不给出不安全承诺。宿主尚不存在时，不应把“宿主实际配置已确认”设为本轮发布门禁。

## 6. T001～T009 自洽性

### 6.1 已自洽部分

- T001～T007 从公共契约、精确任务身份、Base 运行模板到各 Agent 迁移和风险复核，依赖顺序合理。
- T004、T005、T006 在 T003 后并行，符合模块边界。
- T002 的 Redis 租约是内部临时契约变更，不需要 SQL/DDL 或生产数据迁移。
- T008 将独立 Spec Review、Code Review 和 Evidence Matrix 放入 S2 门禁，符合实现者与裁判分离原则。

### 6.2 不自洽部分

- 当前依赖是 `T007 -> T008 -> T009`，但 T008 定义为“完整回归与最终评审”，且 AC 范围只到 AC-009；T009 在评审后才实现 AC-010，会导致最终 Review 无法覆盖最终代码和全部 AC。实施时事实上已经先完成 T009，再启动 T008，说明规划依赖与实际执行顺序不一致。
- 推荐调整为 `T007 -> T009 -> T008`，由 T008 统一覆盖 AC-001～AC-010；或者将 T008 拆为“前置共享改造评审”和“全量最终评审”。当前功能尚未正式交付，第一种更简单。
- T009 的 Done 写成“四类 Agent 的成功、失败/拒绝、单次执行和双模式一致性测试通过”，现有测试只证明四类成功 call、Base 失败/拒绝和部分双模式，不足以支持该完整陈述。
