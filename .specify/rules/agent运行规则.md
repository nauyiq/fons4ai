# Agent运行规则

> 适用仓库：Fons4AI
> 规则状态：首次生成
> 更新日期：2026-07-13

## 项目适用范围

- 本规则适用于 Fons4AI 仓库内的 Agent 协作、知识库维护、规则生成、SDD 流程、BUG 修复、代码和文档变更。
- 本项目按技术框架/基础设施项目处理，不抽象虚构上层业务领域，不把上层业务系统的模型、流程或数据结构写成本仓库事实。
- 当前项目能力域为 Agent 编排、工具管理、RAG、AI 能力接入；物理模块边界不得直接替代能力域边界。
- Spring AI 是当前实现适配，不得被表述为长期唯一框架；涉及新增框架或模型服务商适配时，必须重新核验能力契约和适配边界。

## 核心原则

- 默认使用中文沟通、编写文档和交付说明。
- 修改代码前必须先理解需求、阅读相关上下文并确认变更边界。
- 修改代码、文档或规则前，必须先读取相关上下文，包括 `AGENTS.md`、命中的知识库文档、已有规则和相关源码。
- 不得凭空猜测业务逻辑、接口、字段、表结构、第三方 API、配置来源、部署方式或生产连接方式。
- 优先复用已有代码、工具函数、组件、配置属性和项目内已建立的扩展点。
- 优先遵循项目规范、知识库、规则文件和既有代码风格；规则之间冲突时先标记冲突并请求确认。
- 优先遵循项目事实、知识库、规则文件和已有代码风格；用户提供信息与源码或知识库冲突时，必须标记冲突并请求确认。
- 删除文件、覆盖文档、大范围重构、修改数据库结构、调整公共契约或改变能力边界前，必须获得用户确认。
- 源码中的预留能力、TODO、占位实现和部分验证能力必须明确标注，不得写成已交付或生产可用能力。
- 较大新需求默认进入 Fons4AI SDD 工作流；低风险小变更可以轻量处理，但仍必须先调研并说明验证方式。
- 不允许修改与当前需求无关的代码、文档、配置或格式；发现无关脏改时必须保护并忽略。
- 不允许引入新的技术框架，除非需求明确、已有设计批准并完成兼容性评估。

## 实现者与裁判分离

- 实现 Agent 可以完成调研、设计、编码、自检和验证证据整理，但不能单独裁定任务最终完成。
- SDD 或高风险变更必须区分 Implementer、Spec Reviewer、Code Reviewer 和人工 Gate 的职责。
- 涉及 SDD、公共契约、架构边界、数据结构、安全权限、工具治理或运行资源的变更，必须保留独立 Reviewer、CI/测试系统或人工 Gate 的裁判证据。
- 交付说明必须区分“已实现”“已验证”“未验证”“待确认”和“未覆盖风险”，不得把自检结论冒充最终验收。
- 发现需求、设计或知识库事实不足时，应先提出阻塞问题或标记待确认项，不得以实现 Agent 的推断替代用户或 Reviewer 决策。

## 验证门禁

- 完成声明必须基于新鲜验证证据；旧日志、旧测试结果或未复现的经验只能作为参考，不能作为通过证据。
- 每次变更必须提供 Evidence Bundle，至少包含变更范围、读取的关键证据、执行的验证命令或等价检查、验证结果和剩余风险。
- 新增业务行为、公共 API、状态机、安全权限、缓存、数据库、RPC、网关、MQ、限流、事务或跨模块契约时，默认需要测试或可复现实验验证。
- 纯文档、规则、模块骨架或配置草案可以使用结构检查、脚本校验、编译、自检清单或人工 Review 作为等价验证，但必须说明未进行运行测试的原因。
- 环境缺失、依赖不可用或命令失败时，不得声称验证通过；应记录失败命令、失败原因和后续补验建议。
- 知识库或规则文档变更后，应核验标题、路径、适用范围、事实来源、待确认项和禁止编造内容是否一致。

## MCP与外部工具使用规则

- MCP 和外部工具默认视为当前会话能力，不自动成为项目级事实。
- 未经授权的外部系统访问必须保持只读；写入、删除、发布、发送消息或修改远端状态前必须获得明确确认。
- 没有项目级 MCP 配置、团队规范或用户明确要求时，不生成 MCP 工具清单、账号、环境、连接方式或内部地址。
- 使用 MCP、数据库、浏览器、网络检索或其他外部工具前，必须确认工具用途与当前任务相关，并避免泄露 token、账号、连接串、密钥、内部地址和敏感返回内容。
- MCP 或外部服务的查询结果只能作为当前证据来源；写入知识库或规则前，必须能追溯来源并区分项目事实、实现样例和临时环境状态。
- 对工具管理、MCP 接入、Tavily、模型服务、PgVector、Redis/Redisson 等资源的变更，必须核验配置所有权、密钥外置、超时、错误处理和可替换性风险。

## 输出要求

- 交付说明必须说明生成或修改的路径、规则范围、关键证据来源、校验结果、待确认事项和剩余风险。
- 生成文档时应使用简洁中文，优先写硬性约束和可执行规则，避免长篇背景解释。
- 对项目能力、运行链路和配置资源的描述必须区分当前实现、参考链路、预留能力和演进方向。
- 引用源码、知识库、规则或配置事实时，应使用可定位路径；不能用“应该”“可能”包装成已确认事实。
- 若任务要求进入下一阶段工作流，只能给出建议和交接信息，不自动启动知识建模、SDD、BUG 修复或实现流程。

## 禁止事项

- 禁止编造业务领域、业务接口、数据库字段、配置中心、生产环境、第三方服务、发布流程或组织职责。
- 禁止编造接口、编造数据库字段、编造第三方 API 或把未确认样例写成正式契约。
- 禁止把个人本机 MCP、临时工具状态、当前会话连接或未确认外部资源写成团队项目规则。
- 禁止在规则、知识库、日志或示例中写入真实密钥、token、账号密码、连接串、内部地址或敏感数据。
- 禁止未经确认删除旧规则、覆盖文档、大范围重写知识库或将模块边界改写为能力边界。
- 不允许删除核心业务逻辑；确需移除既有能力时必须先说明影响范围、替代方案和回滚方式，并获得确认。
- 不允许修改数据库结构；确需 DDL、迁移脚本或索引变更时必须先完成设计审查、回滚说明和用户确认。
- 禁止把 Spring AI、PgVector、Redis/Redisson、Tavily 或任一供应商实现表述为长期唯一标准，除非已有用户确认或正式项目规则。
- 禁止把未通过验证的实现、TODO、占位代码或失败命令描述为已完成。

## 信息不足时的处理

- 当需求范围、事实来源、合并策略、能力边界、配置所有权、验证方式或用户授权不清晰时，必须先澄清。
- 对暂不能确认但可能影响后续工作的内容，应标记为 `待确认`，并说明影响范围和建议确认方式。
- 当用户文档、知识库和源码事实不一致时，必须列出冲突来源，不得自行选择其中一个作为最终结论。
- 如果知识基线缺失或明显过期，应建议用户显式触发 `fons4ai-knowledge-bootstrap` 或 `fons4ai-knowledge-summary`，不得在规则生成任务中顺手改写知识库正文。
